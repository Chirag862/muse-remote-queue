# muse-remote-mcp v2 — this Muse's image/video as a remote MCP

Streamable HTTP MCP server. Another Muse calls it; this Muse fulfils
the jobs with its own image/video tools (there is no direct Muse
image/video API — see `server.py` header for the honest design).

## Endpoint

- MCP: `POST /mcp?token=YOUR_MCP_TOKEN`
- Health: `GET /` (public)
- Download: `GET /files/<job_id>?token=YOUR_MCP_TOKEN`
- Queue (fulfiller): `GET /queue?token=YOUR_MCP_TOKEN` — jobs with status `queued`
- Upload (fulfiller): `POST /jobs/<job_id>/upload?token=YOUR_MCP_TOKEN` — multipart field `file`

## Tools (exactly 4)

| Tool | Args | Returns |
|---|---|---|
| `generate_image` | prompt, aspect_ratio="9:16" | job_id (async, queued) |
| `generate_video` | prompt, duration=10, aspect_ratio="9:16" | job_id immediately (async) |
| `job_status` | job_id | queued / running / done / failed + download URL when done |
| `download_output` | job_id | direct downloadable file link (`/files/<job_id>?token=...`, Content-Disposition: attachment) |

## Run

```bash
pip install -r requirements.txt   # mcp>=1.0,<2  httpx  uvicorn  starlette  python-multipart
MCP_TOKEN=<long-random> PUBLIC_BASE_URL=https://<your-public-url> PORT=8000 python server.py
```

## Fulfilment

Jobs live in `jobs/<job_id>.json`, outputs in `outputs/<job_id>.<ext>`.
The fulfiller (a cron every 5 min, or the agent directly) does:
1. Find jobs with status `queued` (oldest first, max 1 image + 1 video per run).
2. Generate the media with the Muse agent's own image/video tools.
3. `python fulfill_job.py <job_id> <output_file>` — marks the job done
   (local server), or `python upload_to_render.py <base_url> <token> <job_id> <output_file>`
   when the server runs on Render (same result, remote).

Remote fulfilment (Render) in detail:
- `curl -s "https://<render-url>/queue?token=<token>"` (or `./queue_check.sh <url> <token>`)
  lists queued jobs: job_id, type, prompt, duration, aspect_ratio, created_at.
- Generate the media for one job with the agent's own image/video tools.
- `python upload_to_render.py https://<render-url> <token> <job_id> <file>`
  uploads it; the server saves it as `outputs/<job_id>.<ext>` and marks
  the job done, and prints the public download URL.

## Deploy on Render free (stable public URL, fast downloads)

1. Push this folder to a GitHub repo.
2. Render dashboard → New → Web Service → pick the repo. Render reads
   `render.yaml`: free plan, region Singapore, native Python runtime.
3. `MCP_TOKEN` is generated by Render (`generateValue`). Copy it — it is
   the token the other Muse needs, and the fulfiller needs it for
   `/queue` and `/jobs/<id>/upload`.
4. After the first deploy, Render shows the service URL
   (e.g. `https://muse-remote.onrender.com`). Set `PUBLIC_BASE_URL` to
   it in the dashboard (Environment) and redeploy — otherwise download
   links point at the placeholder.
5. Give the other Muse: endpoint `https://<render-url>/mcp`, the token,
   and the 4 tools. It calls `generate_image` / `generate_video`, gets a
   job_id, polls `job_status`, then `download_output`.

Honest notes:
- Render free sleeps after 15 min idle; the first call after sleep takes
  ~1 min to wake the service. The other Muse's first call may be slow.
- Render's disk is **ephemeral**: `jobs/` and `outputs/` are lost on
  restart/redeploy. The fulfiller keeps a local copy of every finished
  file and can re-upload it; queued jobs lost in a restart must be
  re-submitted by the caller (the job_id will 404).
- The tunnel URL this replaced was temporary and rotated; Render's URL
  is stable, and downloads come from Render's CDN-backed edge, not a
  ~4 KB/s free tunnel.
